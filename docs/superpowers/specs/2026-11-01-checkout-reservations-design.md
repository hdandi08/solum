# Timed checkout stock reservations

## Intent and authorised scope
Protect limited kit stock when multiple customers enter checkout. Deliver and manually test on dev first. Keep production unchanged, preserve current stock, and defer preorders, stock reconciliation and infrastructure load testing. Waitlist contact fields remain name, email and optional phone, saved only by explicit signup; analytics contain no new contact fields.

## Behaviour
A payment step holds one kit for 12 minutes, using the server deadline. Browsing and entering contact details do not hold stock. Both express and card checkout must acquire a hold before receiving a payable Stripe client secret. Hosted and legacy checkout entry points cannot bypass the hold. Show a quiet countdown in the existing blue/bone style. Refresh must not reset it. At expiry, disable new confirmation, preserve buyer details, and offer a fresh stock check. Do not interrupt confirmation already underway.

## Builder decisions
Use existing Postgres, Supabase functions, Stripe and React. Introduce an opt-in backend flag for staged dev rollout. Create an unconfirmed Stripe object first; atomically reserve stock against its immutable ID before exposing its secret/URL. Never expose an unreserved object. Creation failure before reservation cannot strand stock. A reservation row and its stock decrement commit together. A reservation ID cannot be reacquired after release. Request retry keys prevent duplicate Stripe creation where the browser retries the same request.

All payment creation routes use the same hold helper. Reservations are service-role-only and contain kit ID, Stripe resource ID/type, expiry and state, rather than address or contact data. No frontend direct inventory mutation. Before activation, account for old still-payable dev intents/sessions; do not claim they are protected retroactively.

A scheduled worker reconciles expired holds even after the tab closes. For PaymentIntents, only a confirmed canceled status permits release. Succeeded payments become consumed; processing or uncertain/error outcomes remain held and are retried. Hosted Checkout uses Stripe session expiry; completed sessions retain stock while payment resolves. Duplicate cleanup and simultaneous workers cannot return stock twice. Worker failures must be visible in logs and reservations queryable for operational review.

Paid order finalisation atomically consumes a reservation and marks the existing order inventory flag. No second kit decrement. Unreserved legacy paid orders use an atomic flag-and-decrement transaction and remain an explicit rollout risk. Full refunds atomically mark restocked and increment once. Webhook retries must run finalisation for existing orders, not only newly inserted ones. Preserve Apple Pay shipping handling, order emails and affiliate tracking.

## Acceptance
Concurrent last-unit requests yield one hold. No negative available count. Duplicate reserve, payment finalisation, refund and cleanup are idempotent. Payment success versus expiry never makes paid stock available. Cancellation timeout, DB failure and delayed webhooks retain stock until confirmed reconciliation. Countdown survives refresh and handles elapsed deadlines without clearing contact details. Desktop/mobile and express paths tested. Test keys only; customer email harsha@ecompilers.com. Dev GROUND=0 test setup and existing RITUAL stock must not be reset. Enable only after migrations, webhook, worker and payment endpoints are verified together.

Builder check resolutions: explicitly expire hosted sessions through Stripe's API at the 12-minute deadline (its native configured expiry cannot be shorter than 30 minutes). For direct PaymentIntents in `requires_action`, allow five extra minutes for authentication before cancellation. The UI must not unmount an in-flight confirmation. `processing` never releases merely because time passed. Cancellation races with success are resolved by retrieving the authoritative Stripe state on the next worker attempt. These are implementation choices, not additional user promises.

Review corrections: persist full refund intent by payment ID so refunds delivered before order creation/finalisation are reconciled. Persist subscription creation mappings and use Stripe idempotency keys to prevent duplicate recurring charges on webhook retry. Store only a request hash, server timestamp and Stripe customer identifier for stable checkout retries; hosted prices use inline price data. Retrieve current Stripe state before re-exposing a replayed creation response. Editing details cancels the owned payment using its client secret as proof, releases the hold transactionally, then preserves the form for a new attempt. Hosted async payments fulfil only after paid confirmation; terminal async failure releases held stock. A unique first-box payment index prevents duplicate order rows. Dev legacy test resource audit is guarded by project ID, test key and disabled creation flag.
